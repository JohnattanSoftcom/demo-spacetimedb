Le modèle · 05

Tout le reste en découle

Trois piliers fondamentaux

Tables

Stockage transactionnel

Le schéma, déclaré dans le code comme avec un ORM. Relationnel, en mémoire, avec journal persistant.

Reducers

Calcul côté serveur

Des fonctions transactionnelles : validation, droits, règles métier. Tout réussit, ou rien n’est écrit.

Abonnements

Réseau temps réel

Du SQL côté client. Le résultat arrive, puis chaque changement est poussé en continu.

Tout Spacetime repose sur trois piliers. Les tables : le schéma déclaré dans le code, relationnel, en mémoire avec un journal persistant. Les reducers : des fonctions transactionnelles côté serveur, où tout réussit ou rien n'est écrit. Les abonnements : le client écrit du SQL, reçoit le résultat, puis chaque changement lui est poussé en continu.

Tables · 06

Une table, c’est une struct C# annotée

spacetimedb/Lib.cs

[SpacetimeDB.Table(Accessor = "DriverAssignment", Public = true)]
public partial struct DriverAssignment
{
    [PrimaryKey]
    public uint VehicleId;          // un chauffeur par bus
    [Unique]
    public Identity DriverIdentity;  // un bus par chauffeur
    public string DriverName;
    public Timestamp ClaimedAt;
}

Public = true

Les clients peuvent s’y abonner. Sans ce flag, la table est privée.

PrimaryKey + Unique

La règle « un bus, un chauffeur » est garantie par le schéma.

Pas d’ORM, pas de DTO

La même struct sert au stockage et aux types générés côté client.

Une table, c'est simplement une struct C# annotée. Public = true permet aux clients de s'y abonner ; sans ce flag, la table reste privée. PrimaryKey et Unique garantissent la règle « un bus, un chauffeur » directement dans le schéma. Et pas d'ORM ni de DTO : la même struct sert au stockage et aux types générés côté client.

Reducers · 07

Un reducer, c’est du code serveur ordinaire

spacetimedb/Reducers.cs

[SpacetimeDB.Reducer]
public static void ClaimVehicle(ReducerContext ctx, uint vehicleId)
{
    var user = RequireRole(ctx, Role.Driver);   // rôle lu en base
    if (ctx.Db.DriverAssignment.VehicleId.Find(vehicleId) is { } taken)
        throw new Exception($"Déjà pris par {taken.DriverName}.");
    ctx.Db.DriverAssignment.Insert(new DriverAssignment {
        VehicleId = vehicleId,
        DriverIdentity = ctx.Sender,     // jamais un paramètre
        DriverName = user.Name,
        ClaimedAt = ctx.Timestamp,
    });
    Audit(ctx, user.Name, "VEHICLE_CLAIMED", ...);
}

ctx.Sender

L’identité vient de la connexion authentifiée, jamais d’un argument.

throw = rollback

Une exception annule tout. L’appelant reçoit le message d’erreur.

Une transaction

L’affectation et l’audit sont écrits ensemble, ou pas du tout.

Un reducer, c'est du code serveur ordinaire. L'identité vient de ctx.Sender, c'est-à-dire de la connexion authentifiée, jamais d'un argument que le client pourrait falsifier. Si on lance une exception, tout est annulé et l'appelant reçoit le message d'erreur. Et tout le reducer est une seule transaction : l'affectation et l'audit sont écrits ensemble, ou pas du tout.

Un abonnement, c'est une requête SQL qui reste ouverte. La borne de Fribourg Gare s'abonne à SELECT * FROM stop_eta WHERE stop_id = 5. La base évalue la requête et envoie les lignes initiales. Ensuite elle garde la connexion ouverte. Et à chaque commit, elle calcule quelles requêtes sont touchées et pousse uniquement les lignes qui changent : insert, update, delete. Le client n'a jamais besoin de re-interroger.

Cette slide met en mouvement tout ce qu’on vient de voir avec l’exemple TransVille. À gauche, trois clients connectés en WebSocket : le superviseur du PCC et le chauffeur du bus 101 sont abonnés à la table DriverAssignment, la borne de Fribourg Gare n’écoute que les temps d’attente de son arrêt (stop_eta WHERE stop_id = 5). À droite, Spacetime : un reducer, une table et le commit log. Étape 1 : le chauffeur du bus 101 appelle claimVehicle({ vehicleId: 101 }). Pour lui, c’est un simple appel de fonction ; en réalité un message part sur la WebSocket. Son identité, ctx.Sender, vient de la connexion authentifiée : il ne peut pas se faire passer pour quelqu’un d’autre. Étape 2 : le reducer s’exécute dans une transaction. Il vérifie le rôle, vérifie que le bus est libre, insère la ligne 101 · Chauffeur 1 et écrit une ligne d’audit. Tant que la transaction n’est pas terminée, personne d’autre ne voit cette ligne. Étape 3 : COMMIT. La transaction est ajoutée au commit log persistant d’un seul bloc : tout est écrit, ou rien. Étape 4 : juste après le commit, Spacetime regarde quelles requêtes d’abonnement sont touchées. Le superviseur et le chauffeur sont abonnés à DriverAssignment : ils reçoivent la ligne insérée, et seulement elle. La borne n’est pas concernée, elle ne reçoit rien. Étape 5 : les interfaces se mettent à jour immédiatement grâce au cache local du SDK : le superviseur voit la nouvelle affectation, le chauffeur voit « Bus 101 · à vous ». Aucun polling, aucun endpoint REST à écrire. Étape 6 : le chemin d’échec. Un deuxième chauffeur, celui du bus 201, tente aussi claimVehicle(101). Le reducer voit que le bus est déjà pris et lève une exception : ROLLBACK. L’erreur revient uniquement à l’appelant, rien n’est écrit dans le commit log et aucun client ne reçoit de push.

Sans jeton

La base émet une identité anonyme. C’est ce qu’utilise la démo : une identité par onglet.

Le parcours d’une identité, en quatre étapes. Un fournisseur OpenID Connect (Keycloak, Auth0, Google ou SpacetimeAuth) émet un jeton JWT ; le client ouvre sa connexion WebSocket avec ce jeton ; Spacetime vérifie la signature et en dérive une Identity stable. Dans le reducer, ctx.Sender donne cette identité et ctx.SenderAuth.Jwt les claims. On peut refuser les émetteurs inconnus dès ClientConnected. Sans jeton, la base crée une identité anonyme : c’est ce que fait la démo, une identité par onglet.

Les clients parlent directement à la base, mais ça ne veut pas dire qu’ils peuvent tout faire. Le module tourne isolé dans une sandbox WebAssembly. Les écritures passent uniquement par les reducers, où vivent vos règles d’autorisation ; une exception annule toute la transaction. En lecture, les tables sont privées par défaut et les vues ou filtres sont évalués pour chaque client. Et l’identité repose sur OpenID Connect : Keycloak, Auth0, Google, etc.

Outbox : écrire l’état et le message à publier dans la même transaction, puis les envoyer. Sans elle, un crash entre 4 et 5 laisse la base à jour et les écrans sur l’ancien état.

Un opérateur affecte une caméra à un moniteur. Suivons ce clic.

1

PUT api/videoPlayers/{id}/camera — client NSwag, via l’IP virtuelle

2

VideoPlayerGrain.AffectCamera — intercepteurs : mode, journal

3

HTTP → décodeur — grain bloqué pendant l’appel (timeout 30 s)

4

WriteStateAsync — l’état part en blob JSON dans Galera

5

Publish → RabbitMQ — pas d’outbox entre 4 et 5

6

SignalR Clients.All — diffusé à tous les clients des 5 centres

7

OPC UA → SGE Steria — le nœud OPC est mis à jour

7 étapes, 9 composants, 6 copies du même état pour un clic.

On suit un seul clic : un opérateur affecte une caméra à un moniteur. Un : Angular appelle PUT api/videoPlayers/{id}/camera avec le client généré par NSwag, en passant par l’IP virtuelle keepalived. Deux : le contrôleur appelle le grain VideoPlayerGrain.AffectCamera ; les intercepteurs Orleans vérifient le mode d’exploitation et journalisent. Trois : le grain arrête la séquence, dégroupe, puis appelle le décodeur Weytec en HTTP. Pendant cet appel le grain est bloqué, jusqu’à 30 secondes de timeout. Quatre : WriteStateAsync écrit l’état sous forme de blob JSON dans Galera. Cinq : on publie VideoAffectationEvent dans RabbitMQ via MassTransit. Il n’y a pas d’outbox entre quatre et cinq : si le processus tombe entre les deux, la base et les clients divergent. Six : le consumer du Web relaie par SignalR Clients.All, donc à tous les clients des cinq centres, sans filtrage par droits. Sept : le consumer OPC met à jour les nœuds OPC lus par SGE Steria. Résultat : sept étapes, neuf composants, et le même état copié six fois : mémoire du grain, blob JSON, message RabbitMQ, BehaviorSubject Angular, variables OPC, et le fichier Excel de configuration.

1

affect_camera(moniteur, caméra) — un appel de reducer, en WebSocket

1 transaction — moniteur → caméra 41 + ligne au journal, tout ou rien

4 étapes, 5 composants, 1 source de l’état, au lieu de 7 étapes, 9 composants et 6 copies.

Le même clic qu’à la slide 18, cette fois avec Spacetime. Un : l’UI Angular appelle le reducer affect_camera avec le moniteur et la caméra, par la connexion WebSocket du SDK. Pas d’API REST, pas de contrôleur. Deux : le reducer vérifie les droits avec ctx.Sender, écrit la nouvelle caméra du moniteur et ajoute une ligne au journal, dans une seule transaction : tout ou rien. Trois : au commit, Spacetime pousse le changement à tous les clients abonnés : l’UI des cinq centres, la passerelle OPC qui met à jour SGE Steria, et le décodeur lui-même. Le logiciel du décodeur, aujourd’hui une API ASP.NET appelée en HTTP, devient un client Spacetime abonné à ses propres moniteurs : il reçoit l’ordre en même temps que les écrans et lance le flux. Il n’y a pas de bus entre l’écriture et la diffusion, donc plus de problème d’outbox, et plus d’appel HTTP bloquant de 30 secondes côté serveur. Quatre : le décodeur rend compte avec le reducer report_status, le moniteur passe en Ok ou Failed, et c’est de nouveau poussé à tout le monde. Bonus : après un redémarrage, le décodeur se reconnecte et reçoit l’état voulu de ses moniteurs, il se remet tout seul dans le bon état ; et sa connexion ou déconnexion indique s’il est en ligne. Côté copies : l’état vit dans une seule table ; les clients en ont des caches locaux, mais c’est Spacetime qui les tient à jour, pas notre code. Ce qu’il faut prévoir : redéployer le logiciel des décodeurs, une identité par décodeur qui ne voit que ses lignes, et autoriser la connexion sortante du décodeur vers le serveur. La haute disponibilité de Spacetime en auto-hébergé, qui remplacerait keepalived et les deux nœuds, reste à valider.

Le fond du problème · 20

Limite technique ou choix de conception ?

Le bon design devient le comportement par défaut

Orleans

Avec Orleans, l’atomicité entre moniteurs est un effort explicite (transactions, saga, redécoupage) que le projet n’a pas fait.

Spacetime

Avec Spacetime, c’est le comportement par défaut : un reducer est une transaction, et la séparation intention / effet est imposée, puisqu’un reducer ne peut pas faire d’appel réseau.

Pour anticiper la question des collègues qui connaissent Orleans : oui, Orleans 3.2 savait faire de l’atomique. Il y a les transactions distribuées (ITransactionalState et l’attribut Transaction), une saga, ou un redécoupage avec un grain par mur qui possède tous ses moniteurs. Le projet n’utilise aucune de ces options : ce n’est donc pas une impossibilité, c’est un effort qui n’a pas été fait parce que le modèle acteur rend le chemin non atomique plus naturel. Et une partie reste impossible partout : on ne fait pas de rollback d’un décodeur physique. Ce qu’on peut rendre atomique, c’est l’état voulu ; les appareils sont ensuite réconciliés. Spacetime impose précisément ce découpage.

Plus de bus, plus de hub, plus d’API : chaque client lit par abonnement et écrit par reducer.

Même architecture que TransVille. Les grains Orleans deviennent des tables relationnelles et des reducers. RabbitMQ, MassTransit et le hub SignalR disparaissent : la passerelle OPC et l'UI s'abonnent directement aux tables. Ce qui parle au matériel devient un client Spacetime comme les autres : le logiciel des décodeurs s'abonne directement aux moniteurs qu'il pilote, lance le flux, puis confirme par un reducer. L'agent monitoring fait ses pings et SNMP et publie l'état via report_status. Les timers Orleans des séquences deviennent un reducer planifié.

Exploitation · 22

Tout l’état est en base, tout le temps

Voir et corriger le système en direct

Voir

L’état exact du système, à tout moment, en SQL.

$ spacetime sql vms "SELECT * FROM video_player WHERE status = 'Failed'"

id | camera | status

103 | 43 | Failed

Suivre

Chaque changement s’affiche dès qu’il est validé.

$ spacetime subscribe vms "SELECT * FROM journal"

# le même flux que reçoivent les écrans des centres

Corriger

Appeler un reducer à la main, comme le ferait l’UI.

$ spacetime call vms affect_camera 103 12

# droits vérifiés, journalisé, poussé à tous les écrans

Aujourd’hui : l’état vit dans la mémoire des grains et en blobs JSON dans Galera. Modifier le blob en base ne change pas un grain déjà actif.

Un dernier point, très concret pour l’exploitation. Avec Spacetime, tout l’état du système est dans les tables, et chaque reducer est une transaction validée en base : il n’y a pas d’état caché ailleurs. Voir : avec spacetime sql, on interroge l’état réel à n’importe quel moment, par exemple tous les moniteurs en échec. Suivre : spacetime subscribe affiche chaque changement en direct, c’est le même mécanisme que celui qui alimente les écrans des centres. Avec une table journal, on garde aussi l’historique de qui a fait quoi. Corriger : spacetime call appelle un reducer à la main. C’est mieux qu’un UPDATE direct, parce que la correction passe par les mêmes règles que l’UI : vérification des droits de l’identité qui appelle, journal, et diffusion immédiate à tous les clients. Aujourd’hui, l’état est réparti entre la mémoire des grains Orleans et des blobs JSON dans Galera : un grain actif garde sa copie en mémoire, donc corriger la base à la main ne suffit pas, il faut désactiver le grain ou redémarrer le silo. Les noms de base (vms) et de tables sont illustratifs.
