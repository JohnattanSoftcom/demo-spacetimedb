Outbox : écrire l’état et le message à publier dans la même transaction, puis les envoyer. Sans elle, un crash entre 4 et 5 laisse la base à jour et les écrans sur l’ancien état.

Un opérateur affecte une caméra à un moniteur. Suivons ce clic.

1

PUT api/videoPlayers/{id}/camera — client NSwag, via l’IP virtuelle

2

VideoPlayerGrain.AffectCamera — intercepteurs : mode, journal

3

HTTP → décodeur — grain bloqué pendant l’appel (timeout 30 s)

4

WriteStateAsync — l’état part en blob JSON dans Galera

5

Publish → RabbitMQ — pas d’outbox entre 4 et 5

6

SignalR Clients.All — diffusé à tous les clients des 5 centres

7

OPC UA → SGE Steria — le nœud OPC est mis à jour

7 étapes, 9 composants, 6 copies du même état pour un clic.

On suit un seul clic : un opérateur affecte une caméra à un moniteur. Un : Angular appelle PUT api/videoPlayers/{id}/camera avec le client généré par NSwag, en passant par l’IP virtuelle keepalived. Deux : le contrôleur appelle le grain VideoPlayerGrain.AffectCamera ; les intercepteurs Orleans vérifient le mode d’exploitation et journalisent. Trois : le grain arrête la séquence, dégroupe, puis appelle le décodeur Weytec en HTTP. Pendant cet appel le grain est bloqué, jusqu’à 30 secondes de timeout. Quatre : WriteStateAsync écrit l’état sous forme de blob JSON dans Galera. Cinq : on publie VideoAffectationEvent dans RabbitMQ via MassTransit. Il n’y a pas d’outbox entre quatre et cinq : si le processus tombe entre les deux, la base et les clients divergent. Six : le consumer du Web relaie par SignalR Clients.All, donc à tous les clients des cinq centres, sans filtrage par droits. Sept : le consumer OPC met à jour les nœuds OPC lus par SGE Steria. Résultat : sept étapes, neuf composants, et le même état copié six fois : mémoire du grain, blob JSON, message RabbitMQ, BehaviorSubject Angular, variables OPC, et le fichier Excel de configuration.
